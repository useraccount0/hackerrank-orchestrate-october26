# Requirements

This folder turns the challenge files into structured, traceable requirements.
It is the left top of the V-model (see [docs/v-model.md](../docs/v-model.md)).
Nothing in this folder is part of the challenge solution.

Everything here is managed with **[Doorstop](https://github.com/doorstop-dev/doorstop)**, an
open-source requirements tool (LGPL-3.0). Doorstop keeps every item as a small YAML text file
in git and checks the links between items. One small script,
[tools/srctrace.py](tools/srctrace.py), does the one job Doorstop cannot do: prove that every
line of every input file is accounted for.

## What is where

| Path | What it is |
|---|---|
| [sources.yml](sources.yml) | The **baseline**: which input files were converted, at which git commit, with their SHA-256 |
| `src/` | Doorstop document **SRC**: the input files cut into *source units* (verbatim text) |
| `chr/` | Doorstop document **CHR**: the *challenge requirements* written from the source units |
| [ISSUES.md](ISSUES.md) | Conflicts and unclear points found in the input files, waiting for your decision |
| [views/line_map.csv](views/line_map.csv) | Generated: every input line → its source unit → its requirements |
| [views/SRC.md](views/SRC.md), [views/CHR.md](views/CHR.md) | Generated by Doorstop: readable versions of both documents with their links |
| `_build/html/` | Generated by Doorstop on demand, not in git: HTML version with a traceability matrix |
| [tools/srctrace.py](tools/srctrace.py) | The line-coverage tool (`split`, `update`, `check`, `views`) |
| [tools/pip-requirements.txt](tools/pip-requirements.txt) | Exact versions of the tools |

## The two documents

```text
input files (see sources.yml)             SRC (489 source units)          CHR (202 requirements)
AGENTS.md, CLAUDE.md, README.md,   --->   one unit per non-blank line, <---  each requirement links to
agent_trace_instructions.md,              one per code block, verbatim       every unit that states it
problem_statement.md  (872 lines)
```

Links point from the child (CHR) to its parent (SRC). Doorstop shows them in both directions.

### SRC: source units

The tool `srctrace.py split` cut every input file with one fixed rule:

- a fenced code block (from a line starting with ```` ``` ```` to the next such line) is one unit;
- every other non-blank line is one unit;
- blank lines belong to no unit.

**ID = file code + number of the unit's first line.** So the ID tells you the place:

| Code | File | Example |
|---|---|---|
| `AG` | AGENTS.md | `SRC-AG0237` = AGENTS.md line 237 |
| `CL` | CLAUDE.md | `SRC-CL0001` = CLAUDE.md line 1 |
| `RM` | README.md | `SRC-RM0075` = README.md line 75 |
| `AT` | agent_trace_instructions.md | `SRC-AT0130` = agent_trace_instructions.md line 130 |
| `PS` | problem_statement.md | `SRC-PS0126` = problem_statement.md line 126 |

A line inside a code block belongs to the unit of the block's first line (for example
AGENTS.md lines 246–256 are all `SRC-AG0246`).

Attributes of a source unit:

| Attribute | Meaning |
|---|---|
| `text` | The exact text of the line(s), copied by the tool, never typed by hand |
| `file`, `line_start`, `line_end` | Where it comes from |
| `header` | The same place, written as `file:line` or `file:first-last` |
| `disposition` | What kind of line it is (see below) |
| `classified_by` | Who decided the disposition: `rule` (fixed rule in srctrace.py), `ai` (the AI assistant), or `user` (you) |
| `note` | Why, for every unit that is not a requirement |
| `normative` | Doorstop's flag: `true` exactly when `disposition` is `requirement` |

| `disposition` | Meaning | Needs a requirement? |
|---|---|---|
| `requirement` | States something that must be done, or a fact the solution must respect | **yes**, at least one CHR must link to it |
| `heading` | A title or a label such as "Rules:" | no |
| `formatting` | Markdown structure only: `---`, table header and delimiter rows | no |
| `context` | Background, story, or setup help that requires nothing | no |
| `not-applicable` | Written for someone else (AGENTS.md §7 is for the organizers' dataset generator) | no |

### CHR: challenge requirements

Each requirement is one short, checkable statement written from the source units, without adding
anything that the sources do not say. When several files say the same thing, one requirement
links to all of them.

**ID = `CHR-<section><number>`**, for example `CHR-405` = section 4, requirement 5. `CHR-400` is
the title of section 4.

| Section | Topic |
|---|---|
| 1 | Purpose and scope |
| 2 | Inputs (dataset contract) |
| 3 | Deletion audit logic |
| 4 | Output file (`output.csv` and `steps_json`) |
| 5 | Solution constraints |
| 6 | Submission deliverables |
| 7 | Evaluation by the organizers |
| 8 | Development process and chat transcript |
| 9 | Agent trace submission |

Attributes of a requirement:

| Attribute | Values | Meaning |
|---|---|---|
| `party` | `system` | The deletion-audit solution we will build |
| | `participant` | You (the team): submission, packaging, interview |
| | `coding-agent` | The AI coding assistant during development (log.txt rules etc.) |
| | `organizer` | HackerRank: how they evaluate (a fact for us, not a task) |
| `kind` | `purpose`, `interface`, `functional`, `constraint`, `deliverable`, `process`, `evaluation` | What the requirement is about |
| `modality` | `shall` | Must be done |
| | `should` | Recommended |
| | `may` | Allowed (a freedom) |
| | `fact` | A definition or a statement of how something is; no action, but the design must respect it |
| `verification` | `test`, `inspection`, `analysis`, `demonstration`, `n/a` | How we plan to check it later (right side of the V) |
| `issues` | `ISS-…` | Open points in [ISSUES.md](ISSUES.md) |
| `note` | text | Extra explanation |

## How to trace

**From an input line to its requirements:** open [views/line_map.csv](views/line_map.csv) and
find the file and line. Or build the ID yourself (`problem_statement.md` line 126 → `SRC-PS0126`)
and search for it in [views/SRC.md](views/SRC.md), which lists the *child links*.

**From a requirement to its input lines:** open the requirement in [views/CHR.md](views/CHR.md)
(or `chr/CHR-405.yml`). Its *parent links* are source-unit IDs, and each ID contains the file
and line.

## Setup (once)

Windows PowerShell, from the repository root:

```powershell
python -m venv .venv-req
$env:PYYAML_FORCE_LIBYAML = "0"
.venv-req\Scripts\python -m pip install --ignore-requires-python -r requirements\tools\pip-requirements.txt
```

Why the two extra settings: Doorstop 3.2 officially stops at Python 3.14 but works on 3.15
(`--ignore-requires-python`), and PyYAML has no ready-made Python 3.15 package for Windows yet, so
it is built in its pure-Python form (`PYYAML_FORCE_LIBYAML=0`). On Python 3.14 or older, both are
harmless. On macOS/Linux use `.venv-req/bin/` instead of `.venv-req\Scripts\`.

## Everyday commands

Run from the repository root (PowerShell):

| Purpose | Command |
|---|---|
| Prove that every input line is covered, verbatim | `.venv-req\Scripts\python requirements\tools\srctrace.py check` |
| Check links and coverage, read-only | `.venv-req\Scripts\doorstop -F -W` |
| Same, plus list everything you have not reviewed yet | `.venv-req\Scripts\doorstop -F` |
| Count items waiting for your review | `(Select-String -Path requirements\src\*.yml, requirements\chr\*.yml -Pattern "^reviewed: pending-user-review").Count` |
| Mark one item as reviewed by you | `.venv-req\Scripts\doorstop review CHR-405` |
| Regenerate the views after a change | `.venv-req\Scripts\python requirements\tools\srctrace.py views` then `.venv-req\Scripts\doorstop publish SRC requirements/views/SRC.md` and `.venv-req\Scripts\doorstop publish CHR requirements/views/CHR.md` |
| HTML version with traceability matrix | `.venv-req\Scripts\doorstop publish all requirements/_build/html`, then open `requirements/_build/html/index.html` |

What a clean result looks like:

- `srctrace.py check` ends with `RESULT: PASS`.
- `doorstop -F -W` prints only the document tree (`SRC` → `CHR`) and no `WARNING` or `ERROR` lines.
  For example, `no links from child document: CHR` would mean a requirement line has no
  requirement, and `no links to parent document` would mean a requirement has no source.

## Reviewing (your approval)

- Every item that contains AI judgment starts with `reviewed: pending-user-review`. Doorstop
  reports these items as `unreviewed changes`. Right now that is 394 source units (their
  classification) and all 211 CHR items.
- The 95 source units that were classified by the fixed rules only (headings, `---`, table header
  and delimiter rows) were stamped as reviewed automatically by Doorstop, because nothing in them
  depends on judgment. The rules are in `srctrace.py` and are re-checked by `srctrace.py check`.
- `doorstop review <ID>` stores a fingerprint of the item. If the item changes later, Doorstop
  reports it as `unreviewed changes` again, and every link to it as a `suspect link`, until it is
  reviewed again (`doorstop review`) and the links are confirmed (`doorstop clear`).

## Rules for changes

- **Never edit the `text` or the line numbers of a source unit by hand.** They come from the files;
  `srctrace.py check` fails if they differ.
- To change a classification: edit `disposition` (and `normative`, `note`), set
  `classified_by: user`, then run `srctrace.py check` and `doorstop -F -W`.
- To change a requirement: edit `chr/CHR-….yml` (or use `doorstop edit`). Keep at least one
  parent link to a `requirement` source unit.
- If the organizers change an input file, move the baseline. This was done once already, in
  [step 1.1](../docs/steps/step-01.1-rebaseline-agents-url-fix.md):
  1. In `sources.yml`, set `baseline_commit` to the organizers' new commit and add it to the
     history comment. This is the only decision; everything else follows from it.
  2. Run `srctrace.py check`. It fails and prints the new SHA-256 and line count of every changed
     file. Copy those values into `sources.yml`.
  3. Run `srctrace.py update`. It rewrites the text of every source unit whose line changed in
     place, and lists what needs a decision. Unit IDs contain line numbers, so if lines were
     added, removed, or moved in a file, the IDs shift. In that case it changes nothing in that
     file and reports it, because the units and their links must then be re-mapped by a person.
     It also reports units whose label must be decided again.
  4. Run `srctrace.py check` (must PASS) and `doorstop -F -W`. Every requirement that links to a
     changed unit is reported as `suspect link`. Re-read it, change it if needed, and confirm it
     with `doorstop clear <ID>`.
  5. Regenerate the views.

## Good to know about Doorstop

- Doorstop runs `git add` on every item file it saves (during validation without `-F`, and in
  `review`, `clear`, `add`, `edit`). It never commits. That is why the checks above use `-F`
  (read-only). To unstage a file Doorstop staged: `git restore --staged <file>`.
  (`srctrace.py update` saves through Doorstop with this switched off, so it stages nothing.)
- On Windows, Doorstop writes item files with CRLF line endings; git stores them with LF.
